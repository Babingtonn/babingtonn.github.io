## 1. ІДЕЯ, ПРОДУКТ І БІЗНЕС-МЕТА

### 1.1. Що створюємо

Преміальний, сучасний і швидкий сайт-візитку умовного польського барбершопу **BLACKLINE BARBER**. Це завершений приклад роботи, який власник проєкту зможе показати барберам, салонам і малим бізнесам як доказ своєї здатності створити сайт.

Сайт повинен відповідати на шість питань відвідувача:

1. **Хто ви?** — назва, характер закладу, фотографії.
2. **Що ви пропонуєте?** — перелік послуг.
3. **Скільки це коштує?** — зрозумілі ціни, у демонстрації позначені як приклад.
4. **Чи подобається мені результат робіт?** — галерея.
5. **Де ви і як зв'язатися?** — контакти (тільки після отримання реальних даних).
6. **Як записатися?** — основний заклик `Umów wizytę`, що в реальному проєкті відкриває профіль бізнесу в Booksy.

### 1.2. Бізнес-мета

- Зробити не навчальний «Hello World», а візуально переконливий продукт, який не соромно включити до портфоліо.
- Навчитися повному циклу: бриф → архітектура → макет → розробка → перевірка → публікація → підтримка.
- Отримати структуру і процес, які можна безпечніше повторно використовувати для кафе, кав'ярні, салону краси, студії масажу тощо.
- Показати в демонстрації центральний сценарій: **людина побачила сайт → роздивилася послуги/роботи → натиснула запис**.

### 1.3. Для кого сайт

- Люди в Польщі, які шукають барбершоп і заходять переважно зі смартфона.
- Відвідувачі з Instagram, Google Business Profile, реклами або QR-коду.
- Потенційний власник бізнесу, який оцінюватиме якість твого вебпортфоліо.

### 1.4. Основні критерії успіху

1. Сайт справляє професійне враження **на телефоні** і комп'ютері.
2. До послуг, галереї та кнопки запису можна дістатися за секунди.
3. Немає зламаних посилань, горизонтальної прокрутки, накладень елементів, невидимого тексту.
4. На звичайному мобільному інтернеті сайт відкривається швидко.
5. Більшість контенту легко замінити під реального клієнта, не змінюючи архітектуру.
6. Для розгортання достатньо завантажити статичні файли на хостинг.

## 3. ТЕХНОЛОГІЧНИЙ СТЕК ТА АРХІТЕКТУРА

### 3.1. Вибраний стек

- **HTML5** — структура сторінки, семантика, метадані.
- **CSS3** — дизайн, адаптивність, змінні кольорів, композиція.
- **JavaScript (vanilla)** — тільки мінімальна інтерактивність: мобільне меню, дрібні UI-функції.
- **Git** — контроль історії й повернення до стабільного стану.
- **Локальний перегляд** — Live Server у VS Code або інший простий статичний сервер, без обов'язкового збірника.
- **Статичний хостинг після готовності** — Cloudflare Pages або аналог, з можливістю домену `.pl`.

**Чому без React:** на одну презентаційну сторінку немає вагомої причини вводити фреймворк, залежності, складний процес збірки й додаткові витрати ресурсів старого ноутбука.

### 3.2. Цільова структура файлів

```text
blackline-barber/
├── PLAN.md                    # головний документ із вимогами
├── AGENTS.md                  # короткий регламент AI і розподіл ролей
├── PROGRESS.md                # завершені етапи, відкриті задачі, наступний крок
├── README.md                  # як запустити, структура, як замінити дані
├── .gitignore
├── index.html                 # одна публічна сторінка
├── css/
│   └── styles.css             # стилі, токени, медіазапити
├── js/
│   └── main.js                # мінімальна взаємодія
├── assets/
│   ├── images/                # локальні оптимізовані фото
│   ├── icons/                 # за потреби локальні SVG-іконки
│   └── favicon.svg            # власна проста іконка
└── docs/
    ├── CONTENT.md             # усі тексти, змінні дані та їхній статус
    ├── QA_CHECKLIST.md        # ручні й автоматичні перевірки
    └── HANDOFF.md             # заміна бренду, Booksy, домен, передача клієнту
```

Папки створювати поступово, коли вони реально потрібні. Не генерувати сотні пустих файлів. Усі шляхи — відносні, щоб сторінка працювала локально й на хостингу.

### 3.3. Контрольовані дані бізнесу

Поки немає реального замовника, дані зберігати як **плейсхолдери** з чітким статусом, наприклад:

| Поле | Початкове значення | Правило |
|---|---|---|
| `BUSINESS_NAME` | BLACKLINE BARBER | вигадана навчальна назва |
| `CITY` | `[MIASTO]` | не вигадувати фактичну адресу |
| `PHONE` | `[TELEFON]` | не створювати `tel:` без справжнього номера |
| `EMAIL` | `[EMAIL]` | не створювати `mailto:` без справжньої адреси |
| `ADDRESS` | `[ADRES]` | не виводити фальшиву карту |
| `BOOKSY_URL` | `[BOOKSY_URL]` | не підставляти випадковий профіль бізнесу |
| `INSTAGRAM_URL` | `[INSTAGRAM_URL]` | не підставляти чужий профіль |
| `OPENING_HOURS` | `[GODZINY]` | не вигадувати, якщо позиціонується як реальний заклад |
| `SERVICE_PRICES` | демонстраційні | позначити як приклад, узгодити для реального клієнта |

У файлі `docs/CONTENT.md` підтримувати таблицю «поле → поточне значення → демонстраційне/підтверджене → джерело → дата погодження». У публічному демо не показувати технічні `[PLACEHOLDER]` як начебто реальні контакти: краще приховати незаповнений блок або явно повідомити, що це проєкт-приклад.

### 3.4. Booking через Booksy

- У V1 **немає інтеграції з API Booksy**.
- Справжня кнопка в майбутньому просто відкриває перевірене посилання на профіль конкретного барбершопу.
- URL надає власник бізнесу; перевірити, що це саме його профіль і бронювання доступне.
- Кнопки повинні працювати однаково у hero, секції послуг і наприкінці сторінки.
- Якщо URL ще немає, демонстраційна кнопка **не вдає реальне бронювання**. Допустимі варіанти: показати пояснення «Projekt demonstracyjny — rezerwacja niedostępna» або вести до секції контакту з поясненням. Ніякого `href="#"`, який нічого не робить.
- Коли зовнішнє посилання відкривається в новій вкладці, використовувати `target="_blank" rel="noopener noreferrer"`; на телефоні перевірити поведінку.

## 4. ВІЗУАЛЬНИЙ НАПРЯМОК / ДИЗАЙН-СИСТЕМА

### 4.1. Настрій бренду

Преміальний, чоловічий, стриманий, впевнений, чистий. Не «ігровий» неон, не глянцева шаблонна сторінка з десятками ефектів. Ключовий ефект — **сильна фотографія + чітка типографіка + простір + переконливі CTA**.

**Умовні референси за принципами**, без копіювання чужого дизайну: редакційний мінімалізм, barbershop / editorial photography, темні контрастні фони, помірний металевий акцент.

### 4.2. Кольори

```css
:root {
  --color-bg: #101010;            /* основний темний фон */
  --color-surface: #191919;       /* картки і блоки */
  --color-surface-light: #242424; /* підняття поверхні */
  --color-text: #F5F1EB;          /* основний світлий текст */
  --color-muted: #BCB7AF;         /* другорядний текст */
  --color-accent: #C9A46C;        /* теплий бронзово-золотий */
  --color-accent-text: #15110C;   /* текст на золотих кнопках */
  --color-border: #3B3936;
}
```

Це **початкова гіпотеза**, а не остаточний дизайн. У першому дизайн-етапі Gemini може запропонувати 2–3 варіанти на обговорення. Фінальну палітру затверджує власник. Перевірити контраст, особливо дрібного золотистого тексту.

### 4.3. Типографіка

- Заголовки: виразний, але читабельний шрифт (наприклад, системний із потужною вагою; спеціальне завантаження шрифтів не є обов'язковим).
- Текст: нейтральний sans-serif, комфортний на смартфоні.
- Розміри через `clamp()` там, де це спрощує адаптивність.
- Базовий текст приблизно 16–18 px, висота рядка близько 1.5–1.65.
- H1 — один на сторінці; H2 для основних розділів; не пропускати логіку заголовків без причини.
- На мобільному не робити декоративно розтягнутих заголовків, що обрізаються.

### 4.4. Компоненти

1. **Primary CTA:** заповнена кнопка акцентного кольору з темним читабельним текстом.
2. **Secondary CTA:** прозора/контурна кнопка для другорядних переходів.
3. **Section title:** маленький надзаголовок і великий заголовок, за потреби короткий опис.
4. **Service row/card:** назва, стислий опис, вартість, роздільник.
5. **Gallery item:** фото з однаковою логікою радіусів/співвідношень сторін.
6. **Navigation link:** зрозумілий hover + видимий focus, активність якщо потрібна.
7. **Demo label:** ненав'язливе, але очевидне пояснення «Projekt demonstracyjny».

### 4.5. Анімації

- Мінімальні: зміна кольору, opacity, легкий рух кнопки, відкриття меню.
- Дозволена тривалість переважно 150–300 ms.
- Без складних scroll-jacking і важких бібліотек.
- Якщо користувач увімкнув `prefers-reduced-motion`, рух вимикати або мінімізувати.

- На вузькому екрані компактна навігація з кнопкою меню `aria-expanded`, `aria-controls`.
- Навігація веде на робочі ID секцій; після кліку мобільне меню закривається.
- Якщо header sticky, anchor-мітки не повинні ховатися під ним (`scroll-margin-top`).

**Прийняття:** усе доступно мишею, дотиком і клавіатурою; немає стрибків макета.

### 5.2. Hero — перший екран

**Мета:** за 3–5 секунд показати преміальність і основну дію.

Елементи:

- Велика атмосферна фотографія майстра, інтер'єру або деталей інструментів із легальним правом використання.
- Невеликий надзаголовок: `Twój styl. Nasza precyzja.`
- H1: `BLACKLINE BARBER` або `Fryzjerstwo z charakterem.` (остаточна формула затверджується на дизайн-етапі).
- Підзаголовок: `Męskie strzyżenie i pielęgnacja brody w dopracowanym stylu.`
- CTA `Umów wizytę`.
- Другорядний перехід `Poznaj nasze usługi`.
- За потреби декоративний номер секції або коротка інформація без вигаданих гарантій.

**Прийняття:** H1 читається на фото; CTA видно без пошуку; текст не обрізається на 320–360 px.

### 5.3. O nas

**Мета:** пояснити атмосферу й підхід, не перевантажуючи текстом.

- Заголовок `Więcej niż strzyżenie.`
- 2–3 короткі абзаци польською; докладні бізнес-факти тільки після верифікації.
- Фото робочого простору або інструментів.
- 2–3 принципи: `Precyzja`, `Styl`, `Dbałość o detale`.
- Жодних вигаданих «10 lat doświadczenia», «5000 klientów» тощо.

**Прийняття:** добре читається на мобільному; фото не ламає сітку; немає вигаданих фактів.

### 5.4. Usługi i cennik

**Мета:** людина швидко бачить послуги, варіанти та ціну.

Попередні **виключно демонстраційні** позиції (ціни погодити перед реальним запуском):

| Послуга польською | Демо-опис польською | Демо-ціна |
|---|---|---|
| `Strzyżenie męskie` | `Strzyżenie dopasowane do Twojego stylu.` | `od 70 zł` |
| `Strzyżenie brody` | `Kontur, modelowanie i pielęgnacja.` | `od 50 zł` |
| `Combo: włosy + broda` | `Kompleksowa usługa w jednej wizycie.` | `od 110 zł` |
| `Strzyżenie maszynką` | `Precyzyjna, krótka fryzura.` | `od 50 zł` |

Вимоги:

- У демо є позначка, що ціни прикладові.
- Назви й ціни легко замінити.
- Не додавати прихованих платежів чи неправдивих знижок.
- Кнопка під переліком: `Zarezerwuj termin` / демо-пояснення.
- На мобільному не перетворювати список послуг на незручну горизонтальну таблицю.

### 5.5. Galeria

**Мета:** показати атмосферу і потенційну якість робіт.

- 6–8 оптимізованих зображень для V1.
- Стартовий набір: інтер'єр, інструменти, процес роботи, стилізовані стрижки.
- Не називати стокові фотографії «наші роботи»; у демонстрації вказати, що фото ілюстративні.
- Сітка: 1 стовпчик на вузьких телефонах, 2 на середніх, 3 (або осмислена асиметрія) на широких.
- Можна почати **без лайтбокса**. Якщо з'явиться лайтбокс — він має закриватися Escape, керувати фокусом, мати доступні назви.
- Картинки локальні, оптимізовані, із зазначеними width/height для уникнення зміщення.

### 5.6. Контакт і локалізація

**Мета:** показати можливості зв'язку, не вигадуючи дані.

У реальному клієнтському проєкті:

У поточному **демо**:

- Показати привабливий дизайн секції, але незаповнені контакти не мають виглядати як справжні.
- Допустимо текст `To projekt demonstracyjny. Dane kontaktowe zostaną dodane dla rzeczywistego salonu.`

## 6. МОБІЛЬНИЙ ДИЗАЙН І ПОВЕДІНКА

### 6.1. Принцип mobile-first

Сайт починається з макета для смартфона. Десктоп — розширена версія цього ж досвіду, а не окремий «головний» макет. Більшість клієнтів локальних бізнесів прийдуть із телефона.

**Контрольні ширини для тесту:** 320, 360, 375/390, 430, 768, 1024, 1280, 1440 px; додатково перевірити високу роздільність і масштаб браузера 200%.

### 6.2. Мобільні правила

- Немає горизонтального скролу на стандартних екранах.
- Меню легко відкрити й закрити великим пальцем.
- Кнопки і клікабельні елементи мають комфортні розміри, орієнтир — не менше ~44×44 CSS px для основних дій, де це доцільно.
- Hero на мобільному має осмислене кадрування зображення, а не випадковий обрізаний портрет.
- Довгі польські слова і ціни не «виїжджають» із блоків.
- Фотографії зберігають пропорції і не стають розмитими.
- Верхня та нижня частина екрана враховують безпечні зони смартфонів, коли використовуються фіксовані елементи.
- Немає нав'язливих попапів при першому вході.

### 6.3. Десктопні правила

- Контент обмежений комфортною максимальною шириною, умовно 1160–1280 px, крім повноширинних фонів.
- У hero можливий двоколонковий макет: текст + фото, або full-bleed фото з безпечним градієнтом.
- Сітка послуг і галереї не залишає неприродних великих порожнин.
- Кнопки й посилання мають зрозумілий стан наведення.

### 6.4. Реальні сценарії перевірки

1. Відкрити сайт на телефоні → знайти ціну чоловічої стрижки.
2. Повернутися вгору → перейти у галерею.
3. Натиснути `Umów wizytę` → отримати чесну поведінку демо-кнопки або Booksy в реальному проєкті.
4. Знайти контакт/години/локацію або чітке повідомлення, що дані демо.
5. Перейти між секціями з мобільного меню, закрити меню клавішею Escape, якщо меню реалізоване як розкривний інтерфейс.
6. Оновити сторінку, прокрутити, повторити; не має бути випадкових стрибків чи зависань.

## 7. ДОСТУПНІСТЬ ТА ЯКІСТЬ HTML

### 7.1. Обов'язкові правила

- `<!doctype html>`, `<html lang="pl">`, правильні `meta charset` і `viewport`.
- Рівно один основний `<main>`, семантичні `<header>`, `<nav>`, `<section>`, `<footer>`.
- Рівно один осмислений H1; логічна ієрархія H2/H3.
- Посилання використовувати для переходів, кнопки — для дій. Не робити клікабельні `div` без потреби.
- Усі функції доступні клавіатурою; порядок Tab відповідає візуальному потоку.
- Видимий focus-стан (`:focus-visible`) на інтерактивних елементах.
- Кожне змістовне зображення має доречний `alt` польською; суто декоративні — порожній `alt`.
- Не дублювати довгі «SEO-записи» в alt. Описувати фото чесно.
- Контраст тексту до фону — прагнути до WCAG AA (звичайний текст від 4.5:1, великий від 3:1).
- Меню повинно повідомляти стан `aria-expanded`; доступні назви іконкових кнопок.
- Поважати `prefers-reduced-motion`.
- Посилання «skip to main content» для користувачів клавіатури — бажано включити.
- Не блокувати масштабування.

### 7.2. Антипатерни, які заборонені

- Текст, зашитий усередину фотографій замість HTML, коли це основна інформація.
- Весь сайт як одне величезне `<div>` без структури.
- Зображення без описів або картки, відкривані лише наведенням миші.
- Меню, яке неможливо закрити клавіатурою.
- Фонове відео з автозвуком, миготіння, нескінченні агресивні анімації.
- Контраст «золотий текст на світло-сірому» заради стилю.

## 8. ШВИДКІСТЬ, SEO І ТЕХНІЧНА ЯКІСТЬ

### 8.1. Продуктивність

- Фотографії локальні, оптимізовані у WebP/AVIF або іншому підтримуваному форматі з адекватними розмірами.
- Для картинок нижче першого екрана використовувати `loading="lazy"`, але **не** робити lazy loading головного hero, якщо це шкодить швидкості першого показу.
- Зазначити `width`/`height` або `aspect-ratio` для зменшення зсувів макета.
- Не підтягувати великі JS-бібліотеки заради простого меню.
- CSS/JS мають бути невеликими і зрозумілими.
- Не завантажувати зайві font weights і десятки шрифтів.
- Не використовувати відео у фоні V1, якщо воно суттєво збільшує вагу сторінки.
- За можливості протестувати слабшу мережу та мобільне CPU throttling у DevTools.

### 8.2. Орієнтири якості

Бажані, але не магічні цифри: Lighthouse **Performance ≥90**, **Accessibility ≥90**, **Best Practices ≥90**, **SEO ≥90** у контрольованому запуску. Якщо інструмент показує менше, зафіксувати причину й виправляти пріоритетні проблеми. Не підмінювати реальні результати вигаданими оцінками.

Цільові Core Web Vitals як орієнтир для реального хостингу: LCP до 2.5 с, CLS до 0.1, INP до 200 мс на відповідних умовах вимірювання. На локальному комп'ютері не приписувати тесту реальні польові показники користувачів.

### 8.3. Базове SEO

- Змістовний `<title>` польською без спаму.
- Чесний `meta description`.
- Один H1 і структуровані H2.
- Описові назви файлів: `barber-interior.webp`, а не `IMG_0345.jpg`.
- Open Graph: `og:title`, `og:description`, `og:image` після створення відповідного файлу.
- Favicon і зрозумілий логотип.
- `canonical` **тільки після** того, як є остаточний публічний домен.
- `robots.txt`/`sitemap.xml` можна додати перед індексацією реальної адреси, якщо це має сенс.
- `LocalBusiness` schema.org **тільки для справжнього бізнесу з перевіреними даними**; не створювати фейкову структуровану інформацію про демо-барбершоп.
- Демо-сайт, який не представляє існуючий бізнес, можна залишити неіндексованим до рішення користувача. Не блокувати індексацію реального сайту помилково.

### 8.4. Браузери

Перевірити останні доступні Chrome/Chromium, Firefox, Edge і Safari через реальний пристрій або доступний сервіс, якщо можливо. На Windows без Safari не заявляти «перевірено в Safari», поки справді не протестовано.

## 9. КОНТЕНТ, ФОТОГРАФІЇ, ПРАВА І ПРИВАТНІСТЬ

### 9.1. Тексти

- Усі публічні тексти — природною сучасною польською мовою.
- Назви кнопок короткі й зрозумілі.

- Уточнення, що це демонстраційний барбершоп, повинно бути помітним і чесним.

Прийнятні джерела:

1. Власні фотографії користувача з правом їх використання.
2. Ліцензовані стокові зображення з дотриманням умов ліцензії й атрибуції, якщо потрібна.
3. Згенеровані зображення без відтворення чужих брендів або реальних людей як «співробітників».

Для кожного файлу бажано знати: джерело, дозвіл/ліцензія, чи потрібна атрибуція. Не завантажувати довільні картинки з Google Images. Не використовувати чужі фотографії роботи барбера як роботи вигаданого закладу без чіткого позначення «zdjęcia poglądowe».

### 9.3. Приватність і юридичні межі

- У V1 немає збору персональних даних, форм, авторизації чи бази даних.
- Не вмикати за замовчуванням Google Analytics, Meta Pixel, сторонні чат-віджети й маркетингові cookie.
- Не додавати декоративний cookie banner для повністю статичного демо, якщо немає технологій, що його обґрунтовують.
- Якщо згодом з'являться трекери, форми або сторонні сервіси — до запуску визначити вимоги щодо приватності, cookie та GDPR/RODO для реального польського бізнесу; за потреби звернутися до відповідального фахівця.
- Політики, які зобов'язаний надати бізнес, не заповнювати вигаданими даними власника.
- У репозиторії заборонені паролі, секретні токени, приватні ключі, дані клієнтів.

## 12. ЯК СПІВПРАЦЮЮТЬ CHATGPT, CODEX, GEMINI ТА КОРИСТУВАЧ

### 12.1. ChatGPT — планування та постановка задач

- Допомагає власнику формулювати цілі, вибирати дизайн і приймати рішення.
- Пише **один конкретний промпт під дозволений етап**, а не вимогу створити весь сайт одразу.
- Переглядає звіти Gemini/Codex, допомагає визначати, чи достатньо перевірено результат.
- Вирішує разом із користувачем, коли технічний ризик виправдовує підключення Codex.
- Не перезапускає завершені етапи без причини.

### 12.2. Antigravity + Gemini Flash — ОСНОВНИЙ ВИКОНАВЕЦЬ

Gemini робить **більшу частину повсякденної роботи**, зокрема:

- Створення короткого `AGENTS.md`, `PROGRESS.md`, робочої документації та польських текстів.
- Створення й редагування `index.html`, `css/styles.css`, простого `js/main.js`.
- Дизайн, кольори, шрифти, розмітка секцій, мобільна версія.
- Оформлення послуг, карток, галереї, CTA, контактів, footer.
- Локальні зміни: кольори кнопок, відступи, розміри фото, редагування текстів.
- Підготовка зображень, метаданих, README та нескладних перевірок.
- Перший раунд QA і усунення простих дефектів.

Gemini **не треба** питати Codex про кожну зміну. Але не можна приховувати проблеми чи заявляти, що тести пройдені, коли це не так. Після кожного етапу — зрозумілий звіт і пауза до дозволу користувача.

### 12.3. Codex — ІНЖЕНЕРНИЙ РЕЗЕРВ І КОНТРОЛЬ ЯКОСТІ

Codex використовуємо **цільово, коли він дає відчутну користь**:

1. Складна помилка JavaScript, адаптивності, керування фокусом/доступності, яку Gemini не виправив після двох розумних точкових спроб.
2. Неочевидна архітектурна проблема, конфлікт файлів, регресія або питання, де помилка може дорого коштувати.
3. **Незалежний фінальний технічний аудит** готової версії на етапі 9 перед публікацією.
4. Складні виправлення за результатами аудиту, якщо Gemini не впорається надійно.
5. Проблеми збірки/деплою/домену, коли є реальна технічна складність і користувач погодив залучення.

**Codex не використовувати для:** перекладу рядків, підбору назв секцій, зміни кольорів, заміни фото, більшості базового CSS, простих текстових правок, повторного переписування всього сайту «про всяк випадок».

**Порядок Codex-аудиту:** спочатку вузький запит «перевір і дай список проблем з пріоритетами, нічого не змінюй». Потім користувач вибирає проблеми для виправлення. Не витрачати велику сесію на незатверджений редизайн.

### 12.4. Користувач — власник і фінальний рев'юер

- Обирає дизайн і напрямок.
- Відкриває сайт, перевіряє на своєму телефоні.
- Затверджує кожен етап і дозволяє/не дозволяє підключати Codex.
- Контролює Git-версії, витрати, фото і зміст сайту.
- Поступово розуміє, як працюють HTML/CSS/JS, замість сліпого копіювання змін.

### 12.5. Економія лімітів і контексту

1. На самому початку **Gemini читає весь `PLAN.md` один раз**, робить компактний `AGENTS.md` (орієнтовно до 120 рядків) і короткий `PROGRESS.md`.
2. На кожному наступному кроці агент спершу читає `AGENTS.md` + `PROGRESS.md` + **відповідний розділ `PLAN.md`**, а не все 1100+ рядків без потреби.
3. У промптах вказувати точні файли й коротку мету; не копіювати весь план у кожне повідомлення.
4. Для Codex передавати вузький опис проблеми, спосіб відтворення, конкретні файли й очікувану поведінку.
5. Не просити агента щоразу робити повний редизайн чи читати всі фотографії/коди, якщо треба змінити один елемент.
6. За можливості працювати з локальними файлами; не дублювати великі тексти у чаті без необхідності.
7. **Не встановлювати два важкі редактори одночасно на Dell із 8 GB RAM**, якщо від цього система гальмує: працювати послідовно.

Це **правило організації роботи**, а не обіцянка фіксованого числа токенів або сесій: фактичні ліміти й витрата залежать від доступних інструментів та моделей.

### 12.6. Правило щодо одночасної роботи

**Лише один AI-агент редагує файли проєкту в конкретний момент.** Нормальний цикл: Gemini реалізував етап → власник перевірив → за потреби Codex провів вузький аудит → Gemini виправив просте або Codex виправив складне → користувач погодив перехід. Перед перемиканням агентів перевірити Git-стан, за можливості створити стабільний коміт; ніколи не перезаписувати неперевірені чужі зміни.

## 13. ФОРМАТ КОЖНОГО ЗАВДАННЯ ДЛЯ AI

Кожен промпт повинен мати:

1. **Контекст:** назва проєкту, план, поточний етап.
2. **Мета:** один конкретний результат.
3. **Дозволені файли:** точний список, що можна редагувати.
4. **Заборони:** не зачіпати інші етапи, не додавати залежностей тощо.
5. **Вимоги:** чіткі функції, UX, доступність, мобільність.
6. **Критерії готовності:** що повинно працювати після завершення.
7. **Перевірка:** які команди, перегляди й тест-кейси потрібні.

## 14. ПРАВИЛА GIT, БЕЗПЕЧНОЇ РОБОТИ ТА КОНТРОЛЮ ЗМІН

### 14.1. Що робимо

- Починаючи з першого робочого стану, використовуємо Git.
- Коміти створюємо **після перевірених логічних етапів**, а не для кожного символу.
- Приклад назв: `chore: initialize project`, `feat: add semantic page structure`, `style: implement mobile layout`, `fix: mobile menu accessibility`.
- Перед великим експериментом робимо окремий коміт або гілку.
- Після завершення роботи одного агента другий спершу дивиться поточні зміни й не затирає їх.
- Якщо в папці вже є сторонні файли, не видаляти їх за припущенням «вони зайві».
- Зберігати текстові файли в UTF-8, щоб польські символи не зламалися.

### 14.2. Чого не робимо

- Ніяких `git reset --hard` або примусового перезапису історії без явної потреби й згоди.
- Ніякої автоматичної публікації з неперевіреними контактами.
- Ніяких секретів, токенів або доступів до акаунтів у Git.
- Ніяких «успішних тестів», яких агент не запускав.
- Ніякого масового переписування структури після маленького дизайн-коментаря.

### 14.3. `PROGRESS.md`

Після кожного етапу оновлювати короткий журнал:

```text
# PROGRESS

Поточний етап: 0 / 11
Завершено: ...
Рішення користувача: ...
Що протестовано: ...
Що потрібно протестувати вручну: ...
Відомі проблеми: ...
Наступна задача: ...
Останній стабільний Git-коміт: ...
```

Важливо: `PROGRESS.md` — це щоденник змін, **не заміна** `PLAN.md`.

1. Коротка розмова/бриф.
